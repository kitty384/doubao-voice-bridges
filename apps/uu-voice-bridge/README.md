# UU 远控听写 Fn 2.5.2

在本地 Mac 使用豆包语音输入法，把文字通过网易 UU 远程的文字剪贴板同步粘贴到远端 Mac。豆包在本地录音和转写，远端不用安装本工具。

这是 [DoubaoVoiceBridge](https://github.com/yupeng316888-create/DoubaoVoiceBridge) 的 MIT 派生版本。当前版本为 2.5.2 / build 12，监听实际 Fn / Globe 修饰键，虚拟键码为 `63`；不映射成 Control、F1 或 F10。

## 推荐操作

1. 在本地普通输入框确认豆包自己的 Fn 听写正常，并确认两台 Mac 的 UU 文字剪贴板同步正常。
2. 在 UU 中连接远端 Mac，点击远端要输入文字的位置。
3. 从本工具菜单启用 Fn 听写，**按一次 Fn 打开本地“发送到远端 Mac · UU 远控”输入框**。
4. 框内再使用豆包原生 Fn，按豆包当前的模式开始和结束录音。确认框内出现文字，也可手工编辑。
5. **按 Return 发送**，Esc 取消。存在中文输入法候选或标记文本时，Return / Esc 先交给输入法处理。

请等发送框出现并获得焦点后再按第二次；耳机开框确认到达前的极快第二次点击会被忽略。

这里的“本地发送框”由本工具创建，并非 UU 自带的剪贴板面板。第一次 Fn 负责开框；框内 Fn 交给豆包；Fn 本身不会代替 Return 发送。普通本地输入框里的 Fn 也继续交给豆包。若希望点击开始、再点击结束，请在豆包中设置 Fn 免按模式。

已有未发送草稿时，从同一个 UU 进程和原窗口再请求开框，会恢复原草稿。程序不会因这次开框清空文字，也不会把草稿改发到另一个 UU 窗口。发送期间请保持原连接、窗口和远端输入位置有效，避免切换焦点或改写剪贴板。

默认首次 Fn 即使长按也只开框。菜单「兼容模式：长按 Fn 直接听写」可恢复旧的长按录音、松开后等待转写稳定并尝试自动发送流程；更改此项后需重新启用监听。它依赖合成 Fn 和输入法焦点切换，须单独实测。

## 耳机配合

请配合 [耳机桥接 1.2](../headset-bridge/) 使用。UU 前台的第一次线控点击通过本机 `DistributedNotificationCenter` 请求开框，带有随机请求 UUID、目标 UU 进程号和发送时间；远控桥接检查时效、去重及目标后返回确认。耳机端等待最多约 0.8 秒，失败不补发 Fn，避免迟到开框后又误触发豆包。

发送框获得焦点后，线控点击发送约 60 毫秒、带 `DOUBAO` 标记的 Fn 脉冲，交给豆包。普通本地输入框也采用相同脉冲；是否开始或结束录音取决于豆包的 Fn 模式及其是否接受合成事件。本机开框确认不代表开始录音，也不代表远端已经收到文字。

程序保留对旧耳机 Fn 来源标记的识别，但建议两端同时更新，才能采用本机消息开框。该协作不表示所有耳机或所有豆包版本都已验收。

## 构建

需要 macOS 13 或更新版本、支持 Swift 5.9 或更新版本的 Xcode Command Line Tools。无第三方 Swift 包依赖。

```sh
zsh scripts/test.sh
zsh scripts/build-app.sh
```

生成 `dist/远控听写 Fn.app`，包含 arm64 和 x86_64。构建会校验 Info.plist、双架构和 ad-hoc 签名，并运行纯逻辑自检。脚本只覆盖当前项目 `dist/` 内的同名产物，不安装或启动菜单栏程序。

在有图形桌面的 macOS 会话中，可额外运行 AppKit 布局、事件构造及隔离剪贴板自检：

```sh
BRIDGE_RUN_GUI_SELF_TESTS=1 zsh scripts/test.sh
```

这个选项不会安装全局监听器、注入按键或录音；它需要系统图形和剪贴板服务，不能替代实体 Fn、真实听写和双机验收。`--diagnostics` 是独立的手工诊断命令，构建不自动输出本机状态。

## 安装与权限

1. 退出旧版远控听写，把生成的应用放到固定位置（例如“应用程序”），只启动这一份。配合耳机时也更新并重启耳机工具。
2. 在“系统设置 → 隐私与安全性”中，给当前应用开启“辅助功能”和“输入监控”，完全退出后重新打开。
3. 应用每次启动默认暂停，检查菜单内两项权限状态，再点“启用 Fn 听写”。豆包另行获得麦克风权限，本桥接应用不需要麦克风权限。
4. 若已勾选仍显示未授权，退出应用，移除系统设置里的旧同名条目，重新添加当前固定位置的应用，再启动。重编译的 ad-hoc 签名可能导致旧权限记录不再适用。

本构建没有 Apple 开发者签名或公证。可自行构建，或对可信构建使用 macOS 提供的“隐私与安全性 → 仍要打开”流程；不需要关闭系统安全机制。

## 监听和稳定性边界

启用后会安装全局 HID 事件过滤器；它接收修饰键、按键及部分鼠标事件，只在符合 UU 前台条件时接管 Fn。其他输入放行，主线程处理界面和目标核对。事件回调在独立线程，不同步调用主线程、AppKit 或辅助功能查询。

状态检查使用 common run loop mode，菜单交互期间仍可执行。进入 UU 后约 0.15 秒开始尝试一次有界刷新；发送繁忙或修饰键未松开时保留请求，在安全条件满足后执行。发送清理会明确触发恢复检查，完整规则见下方 2.5.2 说明。旧线程退出后才启动新监听；程序不周期性争抢其他工具的监听顺序，系统停用监听后仍保持暂停。

诊断包含 Fn 按下与松开计数、过滤器和手势阶段、当前是否允许接管、发送框会话状态，不含转写正文。计数和状态便于区分“事件未到达”与“事件到达但当前条件不允许开框”；菜单显示启用本身仍不能证明下一次 Fn 必定可见。

应用有单实例锁。新协作路径减少两个自有工具之间重复触发的机会，但安全输入、第三方过滤器、真实耳机报告和不同 UU / 豆包版本仍需实机验收。

发送会替换并保留系统剪贴板。程序核对本机 UU 进程、窗口及剪贴板后发送 Command-V；没有远端实际收件确认，异步粘贴期间切换焦点仍有误贴风险。详见 [隐私与权限](../../docs/privacy-and-permissions.md)、[排错](../../docs/troubleshooting.md) 和 [验证范围](docs/validation.md)。上游 MIT 声明保留在 [LICENSE](LICENSE)，来源和变更见 [NOTICE](../../NOTICE.md)。

## 2.5.2：发送后的 Fn 恢复

回车发送时，应用会在剪贴板同步期间先把焦点交回 UU。旧版仅在回到 UU 后约 0.15 秒尝试一次监听刷新，此时发送尚在进行，刷新可能被丢弃。新版把前台刷新保存为有界请求，在发送清理完成、修饰键松开且无排队手势后再执行；实际前台查询会补偿遗漏的激活通知。

请求最多保留 5 秒，成功执行一次即消耗；离开 UU、暂停或过期会取消。普通前台切换仍使用 3 秒冷却，实际发送清理完成可请求一次更及时的恢复，最小间隔 0.25 秒。只有原子取得空闲监听器后才计入冷却，不因一次繁忙检查失败而丢掉机会。系统停用监听仍保持暂停。

诊断增加待处理刷新、刷新次数、监听代次及当前修饰键标志，便于区分“未收到 Fn”和“收到但不允许开框”。这些字段没有录音、转写或任意按键正文。

手工验收应在同一 UU 连接中连续重复“Fn 开框 → 输入 → Return 发送 → 不切窗口直接再按 Fn”，同时测试短句、长句与取消。逻辑回归只能证明状态调度，不替代实际 UU、豆包及双机验收。
